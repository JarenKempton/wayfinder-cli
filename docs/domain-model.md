# Portable domain model and capability vocabulary

Status: accepted for protocol 1.x by JWB-276.

This document is the normative vocabulary for Wayfinder CLI's portable core. Tracker,
workspace, and harness adapters translate vendor objects into these terms; they
must not leak vendor identifiers into core behavior.

## Qualified references

| Kind | Form | Meaning |
| --- | --- | --- |
| tracker | `<adapter>:<instance>` | One configured tracker installation |
| workspace | `<tracker-ref>:<workspace-id>` | The v1 dependency and policy boundary |
| group | `<workspace-ref>:group:<native-id>` | An optional container of maps |
| map | `<workspace-ref>:map:<native-id>` | An ordered Wayfinder map |
| ticket | `<workspace-ref>:ticket:<native-id>` | One executable unit of work |
| run | `wayfinder-run:<id>` | One Wayfinder CLI execution session |
| claim | `wayfinder-claim:<id>` | One human-owned claim transaction |

The first five references retain their adapter and instance qualification so
they remain globally unambiguous. Run and claim identifiers are generated by
Wayfinder CLI. V1 may represent cross-map dependencies within one workspace, but rejects
cross-workspace dependency evaluation.

## Entities and ownership

- `Workspace` owns repository policy and the capabilities available at the
  tracker boundary.
- `WorkGroup` optionally nests within another group and contains maps.
- `WayfinderMap` belongs to a workspace, may belong to a group, and preserves
  tracker order for its tickets.
- `Ticket` belongs to exactly one map, has one Wayfinder kind (`task`,
  `research`, `prototype`, or `decision`), and carries normalized state,
  assignment, dependencies, and stable order.
- `Run` is local execution identity. It records the ticket, harness, prepared
  workspace, effective capabilities, and lifecycle state.
- `Claim` is tracker coordination identity. It belongs to a human owner and a
  run, and retains the exact pre-claim snapshot needed for compensation.

A run never substitutes for the human assignee. An expired lease makes a claim
stale; it never authorizes automatic release or reassignment.

## Capability vocabulary

Capability identifiers are lower snake case and describe independently
verifiable behavior. They are additive within protocol 1.x: an adapter may
advertise only behavior it can verify, and a published identifier is not
renamed or repurposed within the major version.

| Boundary | Capabilities |
| --- | --- |
| Tracker structure | `native_maps`, `native_groups`, `native_dependencies`, `cross_map_dependencies`, `native_properties` |
| Tracker mutation | `atomic_assignment`, `workflow_transition`, `conditional_update`, `claim_comments`, `lease_metadata`, `resolution_comments`, `artifact_links` |
| Harness preparation and launch | `prompt_generation`, `workspace_open`, `process_launch`, `session_create` |
| Harness lifecycle | `session_resume`, `session_status`, `session_interrupt`, `session_close` |
| Harness controls | `model_selection`, `reasoning_selection`, `tool_configuration`, `visible_multi_session` |
| Workspace | `workspace_prepare` |
| Development environment | `environment_plan`, `environment_start`, `environment_readiness`, `environment_logs`, `environment_resume`, `environment_stop` |

Presentation tiers such as `prepare`, `launch`, `managed`, and `lifecycle` are
derived summaries, not capabilities. Core authorizes each operation against
its exact required capability set.

## Unsupported behavior

Missing capability support is a normal, explicit failure. Before performing an
operation, core computes the missing set and throws
`UnsupportedCapabilityError` with code `unsupported_capability` and the exact
capability names. It must not invoke the operation, infer success from a nearby
capability, or silently degrade a mutating request. UIs may use the missing set
to explain alternatives, but may not advertise the unavailable operation.
