# JWB-279: Jira, Linear, and GitHub tracker capabilities

Research date: 2026-08-11

## Question

How do Jira Cloud, Linear, and GitHub Issues compare as durable coordination trackers for a portable Wayfinder runtime, especially for maps and child tickets, native work types, blockers, claiming, frontier discovery, lifecycle writes, verification, and concurrent mutation safety?

## Executive conclusion

All three trackers can support the basic Wayfinder transaction—discover tickets, assign a worker, comment, and close—but they do not expose identical guarantees.

- **Jira Cloud has the richest configurable domain model.** Project issue types can represent `Map`, `Research`, `Prototype`, `Decision`, and `Task`; parent fields provide hierarchy; issue links provide dependencies; JQL provides server-side filtering and ordering; and workflows provide explicit transitions. The cost is configuration variability: available types, fields, links, transitions, and permissions must be discovered per project.
- **Linear has the cleanest uniform issue model.** It has parent/sub-issues, explicit blocked/blocking relations, one assignee, workflow states, comments, GraphQL filters, and webhooks. It does not have Jira-style custom issue types; Wayfinder types therefore need a label convention. Its public GraphQL API is unversioned and can return partial data with HTTP 200, so the adapter must inspect GraphQL errors and capability-probe its schema.
- **GitHub now has native sub-issue and issue-dependency REST APIs**, in addition to assignees, comments, labels, state, and issue types. Native issue types are restricted to organization-owned repositories with the feature enabled, so labels remain the portable fallback. Repository issue listing has only a small set of sort keys, while sub-issues have a dedicated reprioritization operation; the adapter should derive frontier order from the map's ordered sub-issue list rather than general issue search.
- **None of the reviewed issue-update APIs documents an atomic “assign only if unassigned” precondition.** A read-then-write claim can race on all three. Consequently, a portable adapter must not advertise verified conditional claim capability merely because it can update an assignee. It should either use a separately proven tracker-specific conditional primitive or report the weaker capability and perform post-write verification with explicit ambiguous/collision outcomes.

## Capability matrix

| Wayfinder need | Jira Cloud | Linear | GitHub Issues |
| --- | --- | --- | --- |
| Map → ticket hierarchy | Native `parent` field; hierarchy depends on project issue-type configuration | Native parent/sub-issues | Native parent/sub-issues; ordered list and reprioritization API |
| Native Wayfinder work types | Configurable project issue types are a strong fit | No general custom issue-type system; use labels | Organization issue types exist only where enabled; otherwise labels |
| Blocking dependency | Configurable issue links; must discover the site's link type and direction | Native blocked/blocking relation | Native `blocked_by` dependency endpoints |
| Claim representation | Assignee field | Single assignee | One or more assignees; Wayfinder must enforce its own single-claim invariant |
| Atomic conditional claim | Not documented by the issue edit/assign APIs reviewed | Not documented by `issueUpdate` | Not documented by issue/assignee update APIs |
| Frontier query | JQL plus explicit `ORDER BY`; enhanced search warns recent writes may lag and offers `reconcileIssues` | GraphQL filtering/pagination; deterministic order must be requested or normalized | Read ordered sub-issues, then filter state/assignee/dependencies; general REST issue list has limited sorts |
| Status/lifecycle | Workflow transitions are separate from ordinary edits | Update workflow-state ID | Update `state`/`state_reason` |
| Resolution comment | Comment API, using Atlassian Document Format in REST v3 | Comment GraphQL operations | Issue comments REST API |
| Change feed | Jira webhooks | Webhooks; Linear explicitly recommends them over polling | Repository webhooks and issue event/timeline APIs |
| API stability concern | Versioned REST v3, but project configuration varies | Public GraphQL API has no version; schema deprecations evolve | Versioned REST API; feature availability varies by owner/repository |
| Authentication | OAuth 2.0 (3LO), Forge/Connect app auth, or email + API token for scripts; permissions remain project/issue specific | OAuth 2.0 for integrations or personal API keys for scripts; OAuth scopes constrain access | GitHub App installation/user tokens, OAuth tokens, or fine-grained PATs; endpoint-specific repository permissions |
| Metadata / adapter-owned data | Configurable custom fields plus JSON issue properties; field visibility/editability varies by project and screen/workflow | Built-in fields and labels through the GraphQL schema; no Jira-equivalent arbitrary project issue-type model | Labels and, for enabled organization repositories, issue types/issue fields; repository custom properties are not issue fields |
| Native leases | None documented for issue claims; assignee plus optional adapter metadata is only a convention | None documented; assignee plus optional label/metadata is only a convention | None documented; assignee plus optional label/body metadata is only a convention |
| Snapshot restoration | Read fields/changelog and issue properties, then issue compensating edits; no general atomic rollback of a multi-step Wayfinder transaction | Query selected fields/relations, then issue compensating mutations; no documented atomic rollback | Read issue/labels/assignees/relations, then issue compensating requests; no documented atomic rollback |
| Pagination | Endpoint-dependent `startAt`/`maxResults`, with `total`/`isLast` not universal; limits can change | GraphQL cursor connections, normally `first`/`after`; default page size is 50 and page size affects complexity | REST `Link` headers with `rel=next`; most list endpoints accept `page`/`per_page` (commonly default 30, max 100) |
| Rate limits | Cost-, quota-, and burst-based limits; handle `429`, `Retry-After`, and `X-RateLimit-*` | Request, endpoint, and GraphQL-complexity budgets; inspect headers and `RATELIMITED` GraphQL errors | Primary resource quotas plus secondary concurrency/point/content limits; handle `403`/`429`, reset and retry headers |

## Jira Cloud

Jira's issue-type resource exposes the issue types visible to a user and the types available in a project, including hierarchy metadata. This makes it possible to verify that the project has the Wayfinder-specific types before advertising native work-type support. The issue edit API can set a parent by key or ID, while status changes are intentionally handled through the separate transition operation. That separation means an adapter should discover editable fields and allowed transitions instead of assuming a universal Jira workflow. [Issue types API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-types/) · [Issues API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issues/) · [Issue transitions API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-transitions/)

Jira issue links can be created, read, and deleted, but issue linking must be enabled and link types are configuration. The adapter should discover link types and record which inward/outward direction means “blocks” rather than relying on a display string. Creating a duplicate link is reported as success and the create response contains no link ID; verification therefore requires rereading the issue's `issuelinks` field. [Issue links API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-links/) · [Jira issue-linking model](https://developer.atlassian.com/cloud/jira/platform/issue-linking-model/)

JQL is the strongest server-side frontier-query language of the three products and can combine project, parent/type, status, assignee, labels, and ordering. However, Atlassian warns that recent updates might not immediately appear in enhanced-search results and documents `reconcileIssues` for stronger read-after-write consistency. A claim transaction should reread the issue directly; it should not treat immediate absence from a JQL frontier result as sole proof of success. [Issue search API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-search/)

REST v3 uses Atlassian Document Format for comment bodies. Jira provides webhook events for issue and comment changes, though webhook filtering and permissions are product/configuration dependent. [REST v3 introduction](https://developer.atlassian.com/cloud/jira/platform/rest/v3/intro/) · [Jira platform webhooks](https://developer.atlassian.com/cloud/jira/platform/webhooks/)

For authentication, Atlassian supports OAuth 2.0 authorization-code grants for integrations and email-address/API-token Basic authentication for scripts; legacy password Basic authentication is deprecated. Authentication does not bypass the per-operation project, issue-security, and global permissions documented by each endpoint. A portable adapter should keep credentials out of process arguments/config receipts and request only the scopes it needs. [Jira OAuth 2.0](https://developer.atlassian.com/cloud/jira/platform/oauth-2-3lo-apps/) · [Basic authentication with API tokens](https://developer.atlassian.com/cloud/jira/platform/basic-auth-for-rest-apis/) · [Authentication deprecation notice](https://developer.atlassian.com/cloud/jira/platform/deprecation-notice-basic-auth-and-cookie-based-auth/)

Jira offers both admin-configured custom fields and issue properties for app-owned JSON data. Issue properties can be read, set, and deleted; the bulk property operation is documented as transactional across its eligible property updates, but that narrow guarantee does **not** make an assignee + transition + comment sequence atomic. No native expiring claim/lease primitive is documented. A lease timestamp stored in a property or custom field is an adapter convention and cannot justify automatic reassignment; the current assignee remains durable claim truth under Wayfinder policy. [Issue properties API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-properties/) · [Fields API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-fields/)

Jira collection pagination is endpoint-dependent. The common envelope uses `startAt`, `maxResults`, and sometimes `total` or `isLast`; Atlassian warns that operation limits can change and `total` can change while paging. A complete frontier read must continue until the endpoint's termination signal and tolerate empty/changing pages. Jira's rate limiting combines quotas/costs with per-tenant, per-resource burst controls; clients should monitor `X-RateLimit-*`, honor `Retry-After` on HTTP 429, and retry with bounded exponential backoff and jitter. [REST pagination and ordering](https://developer.atlassian.com/cloud/jira/platform/rest/v3/intro/#expansion-pagination-and-ordering) · [Jira Cloud rate limiting](https://developer.atlassian.com/cloud/jira/platform/rate-limiting/)

Jira can supply a pre-mutation snapshot through direct issue reads (selected fields, properties, links) and changelog reads. Restoration is a new set of edits and transitions subject to the current workflow, permissions, intervening edits, and side effects; it is compensation, not rollback. The adapter must verify each restored field and surface partial or ambiguous compensation rather than claiming transactional restoration. [Issues API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issues/) · [Issue changelogs API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issues/#api-rest-api-3-issue-issueidorkey-changelog-get)

### Jira adapter implication

Capability discovery is mandatory. At minimum, probe project issue types, parent editability, the blocking link type/direction, assignability, visible transitions, and comment permission. Treat configuration IDs—not human-readable names—as durable API values after discovery. Do not infer conditional claiming from ordinary issue edit or assign operations.

## Linear

Linear's public API is GraphQL, supports schema introspection, and is the same API used by Linear's application. Issues can be queried and created/updated by mutations such as `issueCreate` and `issueUpdate`; updates return both a `success` value and selected issue fields. Linear specifically warns that GraphQL operations can partially succeed with HTTP 200, so checking only transport status is incorrect. [Linear GraphQL guide](https://linear.app/developers/graphql)

Linear natively models parent/sub-issues and explicit blocked, blocking, related, and duplicate relations. These cover map membership and blockers without parsing ticket bodies. Linear issues belong to one team and require a title and status, while other properties are optional. Linear's documented issue model exposes labels rather than a configurable Jira-like issue-type taxonomy, so a portable Wayfinder mapping should use exactly one reserved type label and validate it itself. [Parent and sub-issues](https://linear.app/docs/parent-and-sub-issues) · [Issue relations](https://linear.app/docs/issue-relations) · [Creating issues](https://linear.app/docs/creating-issues)

Manual ordering in Linear list/board views can be workspace-visible, but ordering sub-issues from within a parent can be user-specific. Therefore UI manual order should not be assumed to be a durable global map order unless the API schema and a conformance test prove the relevant ordering field. A safe adapter can maintain map order in an explicit Wayfinder-owned field/body index or normalize a documented API ordering. [Display options](https://linear.app/docs/display-options) · [Parent and sub-issues](https://linear.app/docs/parent-and-sub-issues)

Linear recommends webhooks rather than polling. Webhook payloads reflect the corresponding GraphQL entity and identify the event/entity type in headers. API-key traffic is rate-limited, GraphQL query complexity is also constrained, and rate-limit failures are reported through GraphQL error details. [Webhooks](https://linear.app/developers/webhooks) · [Rate limiting](https://linear.app/developers/rate-limiting)

Linear's GraphQL API is not versioned; deprecations are marked in schema and announced in its changelog. This makes runtime schema probing and contract tests more important than pinning a REST version. [Deprecations](https://linear.app/developers/deprecations)

Linear recommends OAuth 2.0 for third-party integrations and also supports personal API keys. OAuth authorization requests carry scopes, while API keys act as their creating user; the adapter must verify that its actor can see the team and mutate issues rather than treating successful authentication as sufficient authorization. [OAuth 2.0 authentication](https://linear.app/developers/oauth-2-0-authentication) · [GraphQL authentication](https://linear.app/developers/graphql#authentication)

Linear metadata is schema-defined: issues expose built-in properties, labels, relations, and workflow state through GraphQL, and introspection reveals fields available to the caller. No native expiring issue lease is documented. An expiry stored in a label, description, or other writable field is merely a Wayfinder convention; expiration may inform a human decision but must never trigger automatic release/reassignment. Likewise, GraphQL can read a selected snapshot and later submit compensating mutations, but the documentation does not provide a multi-mutation rollback facility. Restoration can fail or overwrite an intervening edit, so every compensated property/relation must be reread and classified independently. [Linear GraphQL guide](https://linear.app/developers/graphql) · [Issue labels](https://linear.app/docs/labels) · [Issue relations](https://linear.app/docs/issue-relations)

Linear GraphQL collections use connection pagination. Its rate-limit guide documents a default of up to 50 records, recommends explicit page sizes, and shows that nested connections multiply query complexity. Clients should follow cursors, request a deterministic sort, and avoid assuming one page is complete. Linear enforces request, per-query/mutation, and complexity limits; response headers expose remaining/reset budgets, and rate-limit failures carry `RATELIMITED` in GraphQL errors. [Linear pagination](https://linear.app/developers/pagination) · [Rate limiting](https://linear.app/developers/rate-limiting)

### Linear adapter implication

Use introspection during development and explicit queries in production, inspect both HTTP status and the GraphQL `errors` array, and verify mutations by rereading the issue and its relations. Labels should carry Wayfinder work type. The public documentation reviewed does not show an expected-version argument on `issueUpdate`; assignment updates must therefore be modeled as non-conditional unless a schema-level primitive is separately proven.

## GitHub Issues

GitHub's REST issue resources manage state, state reason, assignees, labels, milestones, and issue field values. The REST API considers pull requests to be issues too, so list/search results must exclude objects with a `pull_request` member. GitHub permits multiple assignees, which is broader than Wayfinder's single-owner claim rule; the adapter must regard any existing assignee as claimed (or define and verify a narrower repository policy) rather than silently adding another worker. [Issues API](https://docs.github.com/en/rest/issues/issues) · [Issue assignees API](https://docs.github.com/en/rest/issues/assignees)

GitHub has dedicated REST resources for parent/sub-issue relationships. The API can get a parent, list/add/remove sub-issues, and reprioritize a sub-issue. GitHub documents a maximum of 100 sub-issues per parent and up to eight nested levels. This is a natural map index and provides a stable place for map order, subject to the 100-child limit. [Sub-issues API](https://docs.github.com/en/rest/issues/sub-issues) · [Adding sub-issues](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/adding-sub-issues)

GitHub also has dedicated issue-dependency endpoints to list what an issue is blocked by or blocking and to add/remove `blocked_by` relationships. Read and write permissions are explicit, and writes can return validation or secondary-rate-limit errors. The adapter can verify dependency mutations by rereading these endpoints. [Issue dependencies API](https://docs.github.com/en/rest/issues/issue-dependencies)

GitHub's issue create API exposes `type`, but documents issue fields/types as available only for organization-owned repositories with the feature enabled. Labels are supported across ordinary repositories and are consequently the portable type fallback. The adapter should advertise native types only after verifying feature availability and permissions. [Issues API](https://docs.github.com/en/rest/issues/issues) · [Issue types](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/adding-issue-types-to-your-organization)

General issue listing can filter by state and labels and sort only by created time, updated time, or comment count. That is not sufficient to reproduce arbitrary map order. Frontier discovery should begin with the parent's ordered sub-issue endpoint, then hydrate/filter children for open state, no assignee, and no unresolved blockers. [Issues API](https://docs.github.com/en/rest/issues/issues) · [Sub-issues API](https://docs.github.com/en/rest/issues/sub-issues)

GitHub REST supports GitHub App installation/user tokens, OAuth access tokens, and fine-grained personal access tokens. Fine-grained tokens and GitHub Apps are permissioned per resource; the issue, sub-issue, dependency, assignee, and comment references specify the required `Issues` repository permission for each operation. An adapter should prefer an app installation token for shared automation and capability-probe every required endpoint because token type, repository selection, organization policy, and permission level can all narrow access. [REST authentication](https://docs.github.com/en/rest/authentication) · [Fine-grained token permissions](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens)

GitHub labels are broadly available issue metadata; organization issue types and issue fields are conditional features. GitHub does not document an expiring issue-assignment lease. A timestamp in a label, issue body, or comment is adapter-owned metadata, not a server-enforced lease and not authority to remove another assignee. Snapshot capture is possible by reading the issue plus its assignees, labels, parent/sub-issues, dependencies, and comments/events, but restoration consists of separate PATCH/POST/DELETE requests. Those requests are not one atomic rollback and may encounter permission changes, secondary limits, or concurrent edits. The adapter must use compensation receipts and post-restore verification. [Issues API](https://docs.github.com/en/rest/issues/issues) · [Labels API](https://docs.github.com/en/rest/issues/labels) · [Issue events API](https://docs.github.com/en/rest/issues/events)

GitHub paginates large REST collections and exposes navigation URLs in the response `Link` header; clients should follow `rel="next"` instead of constructing assumptions about the final page. Endpoints commonly accept `per_page` and `page`; the sub-issue and dependency endpoints document a maximum page size of 100. GitHub enforces primary quotas by authentication/resource and separate secondary concurrency, point, CPU, and content-creation controls. Clients must honor `Retry-After` and `X-RateLimit-Reset`, stop retrying indefinitely, and recognize both HTTP 403 and 429 as possible rate-limit responses. [REST pagination](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api) · [REST rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)

### GitHub adapter implication

Use sub-issues as the map index and issue dependencies as blockers where those endpoints are available, falling back only when capability probing disproves them. Use one reserved label for Wayfinder type unless organization issue types are verified. Filter pull requests out of generic issue results. Assignment remains a weak claim primitive because the reviewed write API does not document an “only if currently unassigned” guard.

## Portable protocol recommendations

1. **Separate support from guarantees.** Model `canAssign`, `canReadAssignee`, and `canConditionallyAssign` as distinct capabilities. The first two are supported across all three; the third is not established by the primary documentation reviewed.
2. **Require a claim state machine.** Read current owner, attempt assignment, reread directly, and classify the result as verified success, definite collision, definite failure, or ambiguous failure. Never auto-release or overwrite another owner during compensation.
3. **Discover semantic IDs.** Cache only verified Jira type/link/transition IDs and Linear workflow/label IDs. GitHub label/type identifiers likewise require repository or organization discovery.
4. **Prefer native relationships but preserve fallbacks.** Use parent/sub-issue and native blocker relations when verified. Use a documented label/body convention only when a tracker or installation lacks the native capability.
5. **Make frontier ordering explicit.** Jira can use explicit JQL `ORDER BY`; GitHub can use parent sub-issue order; Linear needs an API-proven order or a Wayfinder-owned order index. Always add a deterministic tie-breaker.
6. **Verify every write from authoritative reads.** Jira search may lag; Linear may partially succeed at HTTP 200; GitHub can silently omit fields in some create scenarios when the caller lacks permission. Mutation responses alone are not enough.
7. **Keep adapter-specific payloads narrow.** Jira ADF, Linear GraphQL errors/schema evolution, and GitHub's pull-request-as-issue behavior belong in tracker adapters, not the portable orchestration core.
8. **Do not model leases that trackers do not enforce.** All three can store an informational expiry, but none of the reviewed issue APIs supplies an atomic expiring ownership lease. Expires-at metadata must not authorize automatic release or takeover.
9. **Treat restoration as compensation.** Capture the minimum authoritative pre-write snapshot, record every completed mutation, compensate only owned mutations in reverse order where safe, and verify. Never advertise this as atomic rollback.
10. **Centralize pagination and throttling behavior per adapter.** Complete collection reads must exhaust tracker-specific pages/cursors while retaining deterministic ordering; retries must respect provider reset/retry signals and an idempotency-aware budget.

## Evidence boundary

This is a documentation comparison, not a live conformance test. In particular, it does not prove collision behavior under simultaneous assignment, webhook delivery guarantees, ordering stability in Linear's GraphQL schema, or feature availability in a specific Jira site/GitHub organization. Those claims should remain disabled until fake-adapter and live sandbox tests demonstrate collision, verification, compensation, and ambiguous-failure behavior.
